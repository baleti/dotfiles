Picker query DSL

The small query language typed into the search box of every picker in this repo: the fzf-driven tmux pickers (window-search, claude-history, focus-picker), winswitch's grid search, the Quickshell pickers (clipboard, notification, revit-remote, appmenu, app launcher, RSS reader, the Claude usage panel), the images picker, the search command and the Android app. It arrived at independently in window-search.py, was reused in claude-history and focus-picker.py, then reimplemented for winswitch and the clipboard family (first in Rust/GTK - since replaced by Quickshell QML in 2026-09 - then in JS), and finally given one syntax and shared primitives (below). The code no longer exists in four languages' worth of copies; the semantics are what this doc fixes, and ~/.config/dsl/tests.json checks them.

Reading the older sections. Several sections below were written while winswitch and the clipboard/notification pickers were GTK programs sharing a Rust picker.rs/query.rs engine. Both were replaced by QML (WinSwitchQueryDsl.qml, ClipboardQueryDsl.qml, over the shared lib/dsl.js); picker.rs is now a small helper crate (age formatting, cache directory) with no DSL code. Where those sections say "GTK pickers", picker.rs or query.rs, read the QML consumers in the table below - the behaviour they describe is carried by them.

Native apps (2026-10-23). alt-tab (~/.config/hypr/winswitch-ui) and the Super-key launcher (~/.config/hypr/launcher-ui) are standalone Rust programs now, not Quickshell components; the Quickshell launcher (launcher/, QueryDsl.qml) is gone. Where the sections below say "the QML launcher" or WinSwitchQueryDsl.qml, the behaviour is carried by those two programs over the Rust crate described next (alt-tab still hands /fts and /sw to the Quickshell grid, which also serves the mod+Tab group picker).

Rust reference implementation (2026-10-23). ~/.config/dsl/rs (crate pickerdsl) is the most complete implementation of this document: the primitives of dsl.py, a schema-driven engine (parse a query into row filters, column operations, sort, /g and app-owned verbs; evaluate them over rows through a Source trait; auto-shown filter fields; the /ft pattern value glob), /group (via ~/.config/dsl/group.rs), command spans for highlighting, and the whole completion layer (completion context, candidates, verb-stage depth, Ctrl+Space AND-narrowing, accepting a candidate, popup rows, Ctrl+R history matching). A picker supplies a Schema (type names, extra verbs, descriptions, which verbs completion hides) and a Source; nothing else is grammar. When behaviour here is ambiguous, read it and its tests (cargo test in that directory, which also runs tests.json).

Shared code (2026-10-22). The grammar's pure primitives live once per language: ~/.config/quickshell/lib/dsl.js (every QML consumer - launcher, rss-reader, claude-usage, winswitch, the clipboard family - imports it) and ~/.config/dsl/dsl.py (claude-history, focus-picker, window-search, the search command). They hold key resolution (exact name wins, else substring, comma list, alphabetical sort-key expansion), the /verb/keys[/dir] splitter, direction words, the tokenizer (quotes, !), quoted-term matching and the sort comparator. What stays per picker is what depends on its data: the type registry, row values, tokenizer quirks, completion presentation, and the images picker's Rust and the Android app's Kotlin ports (neither can import them). Conformance suite: ~/.config/dsl/tests.json is run by every implementation that can load it (~/.config/dsl/run-tests.sh: Python, QML, and the images picker's cargo test dsl_conformance); when the grammar changes, change the vectors first and the failing implementations are the ones left to update. (It already caught one divergence: the images picker accepted d as no direction because both words contain a d; the rule is a prefix of ascending / descending.) app-launcher action commands. Besides the five verbs, the launcher has /move-to-workspace (exact-matched like the others, not a filter/sort verb): Enter on it opens a second list of existing workspaces for the window that was focused when the launcher opened. Typing filters; Enter moves the window there. A typed name with no exact match offers + new workspace "name", which creates it (numeric names such as 37 included - they are names, not ids) at the smallest unused id above the window's current workspace (Hyprland orders workspaces by integer id and cannot renumber, so this is the nearest free slot after the current one, not guaranteed adjacent) and names it. Esc returns to the app list. /add-workspace [name] adds an empty workspace right after the current one and focuses it. If the id right after the current one is taken, the contiguous run of workspaces above it is shifted up by one (windows move, names kept) so it really lands adjacent; that shift is skipped (first free id instead) when a window in the run is grouped or a run workspace is visible on another monitor; the usual empty-workspace cleanup removes it when focus leaves. No name = current number + 1 if that name is free, otherwise a decimal (590.1, 590.2...). On a decimal workspace (590.1) it continues that series (590.2, ... 590.10, 590.11), never 591.1. /move-workspace is the sibling: the same second list (minus the current workspace, no "new" row), and choosing one moves the current workspace to the smallest unused id above the chosen one (windows move, name is kept, view follows), i.e. to just after it.

images (photo search) - its own grammar, same keys. Not the verb grammar: the verbs are /face <name> (photos showing a registered person) and /clip <text> (CLIP text match), each its own function like /fts because it changes the search space (photos only, ranked by meaning). The per-column tags stay //: //name <text> (file name), //path <text> (folder), //size >5M / <200K (size comparison), and //dm <text> (date modified; 2015-06 substring or >2015-06 / <2015-06). //mime <kind> (a file kind such as image, pdf, code, directory (folders only), or a bare extension) and //ext <.pdf> (//extension; one exact extension, the leading dot optional, case ignored - //ext .csv). Repeated //mime///ext entries OR together, so //ext .jpg //ext .png finds both; !//ext .log excludes one. Tab after //ext offers the commonest extensions in the index. Several filters AND together; bare words act as /clip plus any matching registered person. In photo mode (/clip, /face, bare words) the filters compose left to right and AND: /clip and /face take the words after them up to the next /command or //tag; a //tag takes exactly one value (quote it for spaces), so words after it are not swallowed; //mime and //ext work here exactly as in name search, and ! negates them; and a bare word that is just an extension, such as .jpeg, is a file-name substring filter and never part of the CLIP text. So /clip brick .jpeg is the bricks, kept only where the name contains .jpeg, and /clip brick //ext .jpg //ext .png keeps jpg or png.

Content search (/fts, /full-text-search, /chroma) - images picker and the search command. Anything written before the verb is the ordinary name filter (the default function: words in the full path, !word, //name //path //size //dm //mime //ext); the verb then searches the contents of exactly the files that filter lets through, so monier road /fts masonry support angle finds the files with "monier" and "road" in their path whose text contains all three words. The verb takes the words after it as Recoll query-language terms (words are ANDed, OR, "phrase", -term), and // tags still filter its results wherever they are written, so /fts dgcl design //mime pdf finds PDFs whose contents contain both words. /fts/<index> terms searches one content index (a unique prefix of its folder name is enough, e.g. /fts/part3 cdm; an unknown name is reported as an error), and a first word after the verb that is exactly an index name does the same (/fts part3-books cdm). The names are the fts list in /facets. Only files that are in a Recoll (Xapian) content index can match: a content search never shows a file that has not been content-indexed. Name search (no verb) covers every file regardless. /chroma words is the semantic sibling: files whose text means something close to the words, best first with a score, over the Chroma indexes (/chroma/<index> for one; it does not cover the BM3 collections yet), with the same name filter in front and the same // tags. /fts lists every matching file (no cap per index; a file reachable from two roots is listed once). Its words are Recoll query language, so masonry -support excludes and a leading -term works; the DSL's own !word is accepted as the same thing (masonry !support). All the // tags work on /fts and /chroma results, //dm included (the date comes from the index). Order is relevance (best first) unless a sort is explicit: /s/size, /s/date, /s/name, /s/path, /s/extension, /s/depth (stackable) all apply to /fts//chroma; with no /s the column sort is not applied. One content verb per query: /fts with /chroma, or either with /clip or /face, is reported as an error, as are an unknown index and a verb with no words. For /chroma with any filter (before the verb or a // tag) the nearest 2,000 chunks per index are searched instead of 400, and when fewer than 20 files survive the filters it looks up to 16,000 deep (about 8 s), so a filtered total is "within the nearest chunks", not exhaustive. Checks: ~/bin/index/tools/query_dsl_check.py (compositions and edge cases through the search CLI) and search_cli_check.py.

Revit matches are gron. For .rvt/.rfa/.rte/.rft results the preview pane shows each match as gron lines (json.levels[3].name = "Level 1";, one snippet per matching model element, its fields kept together) instead of a text slice (photos/gron_rvt.py, built on the rvt2text outline; swap outline_leaves when the extractor gets structured output). In the preview pane the text can be selected with the mouse; Ctrl+C or right-click > Copy copies it (Settings can put the pane below the results instead of beside them).

Preview pane. While a /fts query is showing results (list view), a second pane on the right previews the highlighted file: Recoll's own snippets (Query.getsnippets with its default context-word and occurrence limits, so passages and stemmed matches are the ones Recoll's GUI would show), each with its page number when the format has pages, and the matched words in bold. It follows the cursor, is resizable, and is fetched from the search server's /snippets endpoint.

Folder scope (//path). A substring match on the folder path, usable on every search (names, /fts, /clip, /face). gdrive/ stands for the gdrive mount and ~/ for home, so //path gdrive/office matches every file whose path contains that text, not only that folder. Quote a value that has spaces: //path gdrive/"part 3". Example: /fts career essay cdm daniel //path gdrive/"part 3". Folders listed as off by default in the app's config are hidden unless the query contains //path with that folder's keyword. Typing //path then Tab lists matching folders from the whole catalog, which you can page through. !//path gdrive/office is the inverse: every file whose path does not contain that text (see Negation); it never opts an off-by-default folder in.

Caret keys (all DSL search boxes). Ctrl+E moves the caret to the end of the query, as in Emacs. Ctrl+A keeps its usual meaning of selecting everything in the box, so it does not move the caret. Home and End also work.

Keys follow the pickers above: Up/Down or Ctrl+j/Ctrl+k move, PgUp/PgDn page, Home/End jump, Enter opens, Esc closes.

Ordering (/s, /sort). The one place this picker uses the verb grammar: /s/<field>[,<field>...][/asc|/desc], one token, behaves as in /sort below, with these differences. Fields: name, path, size, date-modified (alias dm, date) - the four columns - plus extension, depth (number of path components), which have no column, and pages (page count of local PDFs: the #P column; the first 5000 matches are counted and ordered, non-PDFs come last in both directions). Names resolve like keys (exact, else unique substring; an ambiguous or unknown one such as /s/d makes that /s inert). Repeated /s commands stack instead of replacing, in order: /s/date-modified /s/size (or /s/date-modified,size) sorts by date modified and, among rows with the same date, by size; ties on every key fall back to path order. One direction applies to every key (the last one given). Timestamps and sizes are real numbers, so ascending is oldest/smallest first (no age-style inversion); the default direction is descending (newest/largest first), as is the order with no /s. Clicking a column header edits the query: it replaces any /s with /s/<column> (a second click on the same column appends /asc, a third goes back), so the box always shows what the list is sorted by and the arrow follows the first key. Photo (//clip, //face) results keep their score order. Sorting is done server-side (filesearch.NameTable.query, sort=date,size).

Completion: Tab (or Ctrl+Space when no popup is open) completes the fragment at the end of the query. One candidate completes immediately; two or more open a popup. Stage 1 completes // to one of the tags above; stage 2 completes a person's name after //face. While the popup is open, typing narrows it in place, Up/Down or Ctrl+j/Ctrl+k move its highlight, Tab or Enter accepts the highlighted candidate, and Esc closes only the popup, not the window. Ctrl+Space does not AND-narrow here: the photo grammar has no verb stage to narrow.

See tmux.md for the tmux bindings and rust-tools.md for winswitch and the clipboard-family pickers.

Completion-UI maturity varies - the grammar/semantics above are shared by every row in that table, but not every picker has caught up on how its Tab-completion is presented (see Autocompletion, below, for the current rule: hidden until Tab, and even then only as a popup when there's more than one candidate). winswitch, clipboard-picker, notification-picker, app-launcher, rss-reader and claude-usage all follow it; claude-history followed it from the start (a nested fzf, since it has no in-layout widget tree to put a popup in). focus-picker (2026-09-13) followed the same nested-fzf pattern: the header's quiet [tab → x] hint still shows what a unique candidate would complete to (and Tab still completes it directly, no popup, when there's only one), but 2+ candidates now open a small nested fzf (complete(), run via tab:execute(...)+transform-query(cat ...) - transform-query alone never hands a command the real terminal a nested interactive fzf needs, only execute(...) does, same reasoning as claude-history's own split) instead of silently picking the first one with no way to see or choose the others. window-search still has no completion assistance at all - pre-existing, independent of the popup-visibility rule (nothing pops up there to begin with) - worth bringing forward if its DSL usage grows enough to need it, but not fixed as part of this change.

The shape of it

Every picker shows a result set (windows, panes, clipboard entries, scrollback-bearing windows, ...) with, potentially, several named types per entry - a "type" here is any one field that can be filtered on or shown as a column (title, workspace, pid, age, app; tmux-session, claude-title, ... - a related family shares a hyphenated name prefix, see Keys).

Type names are each picker's own vocabulary, not required to be shared across the table above. Only the DSL's grammar and semantics are meant to stay consistent picker to picker (see the intro above); concrete type names are each picker's own call, and one picker lacking a type another picker has is not automatically a gap to fix. winswitch has tmux-* and claude-* types because its entities - Hyprland windows - only optionally run inside tmux or Claude Code; the pickers whose rows already are tmux entities (focus-picker, window-search, claude-history) name theirs tmux, session, window, pane as they always did. claude-history in particular has a flat type literally named tmux (a session:window.pane display string), which is why it never grew tmux-* siblings.

The DSL does three orthogonal things to that set, and nothing else:

  • filter rows - which entries survive (/filter-value, and bare typed text, which is the same thing)
  • filter columns - which types are shown (/filter-type, /add-type, /remove-type)
  • order - what sequence the survivors appear in (/sort)

This is the SELECT ... WHERE ... ORDER BY triad, in the interactive piped-verb dialect that Kusto/KQL (where / project / project-away / sort by), Splunk SPL (where / fields / fields - / sort) and PowerShell (Where-Object / Select-Object / Sort-Object) all landed on before this. Each /verb token is one pipeline stage; there is no explicit pipe character, whitespace between tokens is the pipe.

Grammar

Reworked 2026-10-22: one syntax, built from slashes and commas only (no dots, no path:value, no space-separated paths or directions).

The search box text is split on whitespace into tokens (a "..."-quoted run stays one token, interior whitespace intact - see Quoting). Each token is either:

/verb/keys[/dir] arg   a command: verb exact-matched, keys = what it acts on (see Keys)
//keys arg             the verb left empty: shorthand for /fv/keys arg (see Default verb)
"phrase"               quoted literal - never a command, always row-filter text
bareword               anything else - an implicit /filter-value argument
!<any of the above>    negated: a leading ! inverts a row filter (see Negation)

The command token has up to three /-separated parts, and each part's role is fixed by its position, which is what keeps the grammar free of guessing: part 1 the verb, part 2 the keys, part 3 (only /sort) the direction.

Token Reads as
/fv/title rvt or //title rvt rows whose title contains rvt
//p rvt rows where pid OR path (any key containing p) contains rvt
//title,path rvt rows where title OR path contains rvt
/s/title sort by title, descending (the default direction)
/s/title,status/asc sort by title, ties by status, ascending
/ft/tmux, /at/claude-title, /rt/pid column verbs, same key list
/fts/claude-live word an app verb (e.g. winswitch's full text) with its own key list

A command's argument is the single value token that follows it (/fv only; /ft /at /rt /s take none - their keys sit in the token itself), up to the next /verb, end of input, or a token that is itself a command. A token past a verb's arity is not absorbed: it resumes as an ordinary token, which, being a plain token with no verb, is a bare /filter-value. /fv is the fallback - every token left over becomes a row filter, never silently dropped. /s/name blender is therefore two things: sort by name, and filter to blender.

A command without keys (/fv, /s, /ft alone) is inert: it takes no argument, so /fv foo is just the bare word foo. A malformed token (too many parts, a direction on a verb that has none, an unknown verb) is inert too and never an error - "half-typed stays a no-op" is the rule everywhere.

Verbs

Short Long Axis Takes Effect
/fv /filter-value rows keys + 1 value keep rows whose value matches; drop the rest
/ft /filter-type columns keys keep only the columns whose name matches; hide the rest
/at /add-type columns keys add the columns whose name matches into view
/rt /remove-type columns keys drop the columns whose name matches from view
/s /sort order keys + optional /dir order rows by the key fields
/g /group view keys + optional bucket / level / /dir fold the rows into collapsible sections

Verb names are exact-matched against exactly these five short and five long forms (plus the empty spelling //, see Default verb) - nothing else, no substring or fuzzy resolution on the verb itself, ever. A type name never sits in verb position, so adding a type can never collide with the verb vocabulary. It is a key's own resolution that is fuzzy (next section), precisely because key position and verb position are kept so strictly separate. An unrecognised /xyz token is inert. Both the short and long form of a verb mean exactly the same thing; autocomplete offers the short forms.

Keys

Part 2 of a command is a comma-separated list of keys. A key names one or more types (a type = any one field that can be filtered on or shown as a column). Resolution, per key:

  1. a type whose name equals the key (case-insensitive) wins, alone;
  2. otherwise every type whose name contains the key (substring) - the key is fuzzy: //p reaches pid and path;
  3. the key list's matches are unioned across its commas (//title,path).

A key that resolves to nothing contributes nothing. A key list that resolves to nothing makes its command inert (for a filter: "narrows to nothing", an honest empty result; for a column verb: a silent no-op). Empty keys (//a,,b, a trailing comma) are skipped, and an entirely empty key list (//, /fv/) is "nothing typed yet": inert, never "matches everything".

Type names are flat. A family of related types shares a name prefix with a hyphen: tmux-session, tmux-window, tmux-pane, claude-title, claude-live, claude-archive, hypr-workspace. There are no groups, no dotted subfields and no *: because keys are substring-matched, //tmux already reaches every tmux-* type, //tmux-win just the window one, and /at/claude adds every claude-* column. Each picker owns its vocabulary (only the grammar is shared). Exact-name-wins keeps a short name from being swallowed by its own family: //title is the plain title, not also tmux-title and claude-title (type //tit or //-title to mean them all).

/sort expands a fuzzy key into every type it reaches, alphabetically (2026-10-22; before, an ambiguous key made the sort inert): /s/pa is /s/pages,path, /s/tmux is /s/tmux-session,tmux-title,tmux-window. The exact name still wins alone (/s/path is just path), a type already in the chain is not repeated, and a key that names nothing makes the whole /s inert. To sort by one type only, name it.

Default verb (//)

/fv is the default verb: leave the verb slot empty and the second / still introduces the keys, to /fv.

//claude ovh          =  /fv/claude ovh
//                    =  /fv/     (nothing typed after yet)

This is the only default the grammar has: // always means /fv/, never /ft/ or /s/. A lone / followed by a word is an unrecognised verb, and a /verb/keys token whose verb is named is unaffected. Everything that holds for /fv/keys holds for //keys unchanged - it is a spelling resolved at tokenizing time: arity (one value token), no-op while the value is pending, Auto-show, inline colouring, quoting ("//foo" is literal; a pasted //host/share has too many parts and is inert, so quote it), completion (// + Tab is the key stage of /fv/).

/fv without a path

At the very start, a search box already behaves as if /fv were prepended: bare words are filters over the free-text haystack (below). That is the only "default" a user needs, so / alone is not a shorthand for /fv.

/filter-value (/fv) - and bare text

Filters which rows survive. Two forms:

  • bare text (text, no verb) - substring-match text (quote it, "5", to match only the standalone 5, not 599), case-insensitively, against the picker's always-present free-text haystack (window title+class+workspace; clipboard preview; pane scrollback; notification app+summary+body; app name + generic name; article title+feed+tag+body). This is the one form every picker guarantees and the one a casual user needs no syntax for; /fv itself needs no spelling here (a lone /fv with no keys is inert, see Grammar). Keep this haystack to short, controlled strings: the app launcher deliberately leaves .desktop Comment= and Keywords= out of it (reachable only as scoped //comment / //keywords), because substring-matching prose mid-word turned ala into a hit on "scalable" and "balance".
  • //keys value (= /fv/keys value) - scope: keep rows where a type matching one of the keys has a value containing value (substring, case-insensitive; see Keys for how fuzzy keys and commas resolve). value prefixed with > < >= <= compares instead of substring-matching (clipboard-picker/notification-picker only, added 2026-09-28 - //lines >4) - reuses /sort's own comparator (compareFieldValues; see "Sort comparison, precisely" below) so a filter and a sort never disagree about what "greater" means for the same field. Only means anything when both the row's value and the operand are one of the two shapes that comparator recognises - plain integers (//chars >500) or age buckets (//age >3h, meaning "older than 3h" - the operator compares the raw stored age, larger is further in the past, no direction-trap inversion the way /s/age/asc needs); anything else (a non-numeric field, or an operand that isn't) never matches, rather than falling back to >4 as literal substring text. No = operator - plain substring already covers loose equality. Not yet ported to any other consumer. Keys alone, with no value yet, are a no-op (never "flash to zero" on a valid partial keystroke, see Design principles) - but the named columns are Auto-shown at once.

There is no "existence" filter (/fv claude used to keep rows that had any value in the claude group): groups are gone (see Keys). To keep only the rows that have a value in a field, match anything in it, e.g. //claude-session ..

Multiple /fv terms (and multiple bare words) are AND-ed, order independent: every one must match a surviving row. Bare words are each their own term (foo bar requires both, independently) except in clipboard-picker / notification-picker, whose bare words join into one space-separated phrase matched as a single contiguous run - that predates this DSL and is left as-is (see ClipboardQueryDsl.qml).

BM25-ranked pickers (window-search, claude-history) keep their own extra row-filter spelling on top of this - prefix-expanded bare words and "phrase" as required exact text - because ranking a large scrollback corpus needs them and an unranked couple-dozen-window grid does not. (! negation used to be on this list; it is now part of the shared grammar, see Negation below.) Those are documented in each script's own header; everything in this doc applies to them unchanged otherwise.

Negation (!)

A leading ! on a row filter inverts it: the term keeps exactly the rows its positive form would drop. Added 2026-10-06 to every consumer that has a row filter (window-search and claude-history already had it, ad hoc).

!alacritty                     rows whose free-text haystack does NOT contain it
!"foo bar"                     ... does not contain the exact phrase
!//path gdrive/office          rows where NO type matching "path" contains the value
!/fv/claude-title ovh          explicit-verb spelling, same thing
!//claude-session .            rows with no claude session at all (see the existence note in /fv)
//lines !>4                    comparisons invert too: rows where "lines > 4" is not true
alacritty !//path gdrive/      terms still AND: contains "alacritty", NOT under gdrive/
  • Where the ! goes. On the term's first token: the verb token (!//path x, !/fv x, !/fv/path x), or the bare word / quoted phrase (!x, !"x y"). A ! on the value token (//path !x) means the same; writing both is still one negation, not a double one.
  • Complement, exactly. For any term T, the rows matching T and the rows matching !T partition the result set. In particular a group scope (!//claude ovh) drops a row if any subfield contains the value (the complement of the positive union rule), a path that resolves to nothing (positive: narrows to nothing) negates to "keep everything", and a row whose value is missing or not comparable (!//lines >4 on a non-numeric row) is kept, because the positive form did not match it.
  • Only row filters. !/s, !/ft, !/at, !/rt parse (so their arguments are still consumed and don't leak out as bare words) but do nothing. Negation is not a column or order operation.
  • Still forming is inert. A lone !, or ! followed by space, is a token still being typed and changes nothing - the same "never flash to zero on a partial keystroke" rule as a half-typed verb. !//path with no value yet is the existing value-pending no-op.
  • Literal !. Quote it: "!important" is the text !important. (The ! must be the first character of the token; a!b is plain text.)
  • Purely negative queries (!foo alone) show everything except the matches. No special case in an unranked picker.
  • Highlighting. A negated term has nothing to highlight in a row that survives it, so match highlighting skips it.
  • Auto-show. !//claude / !//path x still auto-show the field they scope to (Auto-shown filter fields): seeing the value that was not matched is exactly how you check the exclusion did what you meant. The per-subfield "which subfield matched this row" labelling (winswitch) is positive-only and ignores negated terms.
  • Completion and coloring see through the !: it is not part of the command, so !/fv/ + Tab completes like /fv/, replacement keeps the !, and the validity coloring starts after it.
  • Off-by-default folders (images picker). Only a positive //path <keyword> opts a hidden folder in; !//path <keyword> excludes that folder and never reveals it.
  • Not everywhere. Pickers whose engine can't invert a given verb leave it inert rather than guess: in the images picker /clip and /fts take no ! (CLIP "not like X" has no meaning; Recoll has its own -term inside /fts), while !//path, !//name, !//size, !//dm, !//mime, !//ext, !/face <name> (photos without that person) and bare name words work; bare words in photo mode are CLIP text, so a !word there is inert. notification-picker shares ClipboardQueryDsl.qml with clipboard-picker and so has all of it; picker.rs no longer holds a DSL engine.

Where it's implemented. Shared launcher QueryDsl.qml (tokenize strips the ! into neg, parse carries it onto terms, applyNeg is what each consumer's matcher wraps its result in - app-launcher, rss-reader, claude-usage), WinSwitchQueryDsl.qml, ClipboardQueryDsl.qml (clipboard + notification pickers; bare negated words are a separate negWords list because positive bare words are joined into one phrase), focus-picker.py (tokenize(query, negs)), the Android QueryDsl.kt (Token.neg), and the images picker: the egui client only forwards the query (and skips negated terms when highlighting) while the server parses it - filesearch.py (_take_tags files a negated pair under the key "!tag", so positive consumers are untouched; split_neg_terms; NameTable._match) and photos/search.py (parse returns a third negated field; negated filters are subtracted after the AND). claude-history and window-search.py keep their own earlier implementations.

/filter-type (/ft), /add-type (/at), /remove-type (/rt)

Change which columns are shown. Never filter rows - orthogonal by construction. All three take a key list in their token (/ft/title,pid) and are processed left to right against one running ordered set that starts at the picker's default columns:

  • /ft/keys - intersect: keep only the currently-shown columns whose name matches the keys, drop the others. "Filter down to these."
  • /at/keys - union: add every matching column that isn't already shown, at the end.
  • /rt/keys - subtract: remove every matching column.

Order is significant: /ft/claude /at/workspace shows the claude types plus workspace; /at/workspace /ft/claude shows only claude types (the /ft drops the workspace the /at just added). Adding a column that is already shown, or removing/filtering one that is not, is a silent no-op.

Defaults per picker:

  • winswitch: title alone (today's grid label). workspace, pid, and every tmux/claude subfield are hidden until an /at (or a surviving /ft) brings them in. There is no class type at all - it wasn't a useful column or filter key, so it was dropped from the type registry entirely (it still contributes to the free-text haystack alongside title, same as always - see /filter-value, above).
  • clipboard-picker: chars/lines/mime, in that order (chars/ lines: the row's old always-on size badge, now real columns instead - see below; mime: comma-separated MIME types offered, trimmed of any ;parameter such as ;charset=utf-8 for display - see cliphist-store-logged.sh's multi-format bundle manifest in rust-tools.md). mime and age both have a content-fitted width (TextMetrics against the longer of the column's own header label and the longest value among the currently-shown rows, 2026-10-02 - a flat hardcoded floor stayed the binding constraint whenever every visible value was short, reported as the column looking "twice as wide as it needs to be") rather than a fixed one: mime's comma-joined multi-format entries can run long, so it's additionally capped at 30% of the box width so it can never crowd the preview text out entirely; age (a humanize_ago bucket, ^\d+[smhd]$) is inherently short and bounded, so it auto-sizes with no percentage cap and a proportionally smaller padding buffer than mime's (fractional-scale sub-pixel rounding error scales with glyph count - generous padding sized for an 81-character mime string roughly doubles a 2-3 character age value). type/chars/lines stay fixed-width. type/age are hidden until /at'd or Auto-shown by a /fv filter, same as before this feature existed (2026-09-28). age was date until 2026-10-02 - "date" read as a calendar date, the column actually shows elapsed time since copy, same rename reasoning as focus-picker's time -> age.
  • notification-picker: app/age, both on from open - there was no pre-existing "always shown" info to preserve the way clipboard-picker's size badge was, so defaulting both on is what makes the table useful immediately. age auto-sizes the same way clipboard-picker's does (app stays fixed-width).
  • revit-remote picker: input/instance on from open; the command's name is the row's own preview text, so command is only a column after /at command. Fields: command (display name), class, input, output, target, instance (target, Revit year, pid), year, pid, state (idle, or dialog: <title> while a modal dialog holds that Revit up). Free text is display name + class + target + year only; input is deliberately left out so any does not match every command that needs a selection (//input any does). pid sorts numerically.
  • fzf pickers: focus-picker renders columns and honours all three verbs; window-search / claude-history render a single ranked line and ignore column verbs (inert, not an error).

A family prefix as a column key (/at/claude) means every type under it, each its own column; /at/claude-title is just the one.

/sort (/s)

Reorder the survivors; never filter or hide.

  • /s/key1[,key2,...][/dir] - order rows by key1; rows that tie on it are broken by key2, and so on for however many comma-separated keys are chained. Each key resolves like any key (exact name wins, else every type containing it) and a fuzzy key expands into all its types in alphabetical order (/s/pa = /s/pages,path); a key that resolves to nothing makes the whole /s inert, not just that key. /s/tokens alone is the plain single-key sort.
  • /dir, the optional third part: asc / desc (or any non-empty prefix of ascending / descending: a, de, ...). It is taken by position, so it can never be confused with a key or a following word: /s/title,status/desc blender sorts and then filters on blender. No /dir means descending (2026-10-22; was ascending): biggest / newest / last first, and /asc asks for the other way. One direction applies to every key in the chain - there is no per-key direction; to run one key the other way, give it its own second /s and rely on the last-wins replacement. Only the last /s in a query takes effect (replace, not stack) - except in the images picker, where repeated /s stack. A direction on any other verb makes it inert. Absent entirely, the picker's own default order stands (MRU, cliphist recency, winswitch focus-history, BM25 score). Honoured by winswitch, focus-picker, clipboard-picker and notification-picker (2026-09-28); inert in the BM25 pickers (score is the order).
  • The old space forms (/s name desc, /sort name) are gone: the verb takes its keys and direction from its own token only.

Sort indicators. Wherever a picker marks the sort in its column headers, the header of every column named by the typed /s/key1,key2,.../dir is marked: the first key (the primary) with the direction arrow ▲/▼ as before, every further key (a tie-breaker, secondary) with the same arrow in a different colour - so /s/dm,size/desc shows MODIFIED ▼ as the primary and SIZE ▼ in the second colour. A click-sorted header (no typed /s) is always primary. Implemented in the images picker (accent colour primary, text colour secondary), the claude-usage panel (muted primary, accent secondary; its header click and the typed /s share the arrows) and focus-picker (bold primary, cyan secondary, in its fzf header). Pickers with no sortable column headers (alt-tab, clipboard, notification, app-launcher, rss-reader, claude-history) have nothing to mark.

Multi-key chaining dates from 2026-09-02 (then /sort/tokens/title, with / between keys; the comma replaced the slash 2026-10-22 so / can mean "next part").

Sort comparison, precisely. Every type is stored and matched as a string, but plain lexicographic comparison is wrong for two shapes the pickers already have. The comparator (compare_field_values) sniffs both values being compared:

  • Plain integers (workspace, pid, a raw token count): "10" must sort after "2", not before - both sides parse as non-negative ints -> numeric compare. This applies to the underlying value, not a display- formatted one: a token count shown as "58k" sorts on the real integer it came from, not that string (formatted-with-a-suffix strings don't parse as plain ints at all, so without this they'd silently fall to the lexicographic case below and sort nonsensically by leading digit). Reported 2026-09-02 for exactly this field, missed in an early implementation's DSL-driven /sort path - any sort UI a picker offers must share this one comparator, DSL-driven or not (e.g. a clickable column header that also re-sorts the same rows) - two sort entry points disagreeing on "100" vs. "2" because only one of them got the numeric-sniffing treatment is the bug, not a variant worth keeping.
  • Age buckets (age, from humanize_ago - "30s", "5m", "3h", "2d"): comparing the strings is nonsense across units. Both sides match ^\d+[smhd]$ -> convert to seconds and compare that.
  • Otherwise -> lexicographic (correct already for title / app / type).

The direction trap. age's stored value is an age (seconds ago) - smaller means more recent. /s/age/desc means "newest first" in the ordinary calendar sense, which is ascending by age in seconds. So for age-shaped values the requested direction is inverted before it reaches the numeric comparison: ascending (oldest first, chronological) compares age descending internally; descending (newest first) compares age ascending. Plain ints and text apply the direction literally. The trap is specific to "time since" values.

/group (/g)

Added 2026-10-23. Folds the rows into collapsible sections. A view transform: it never filters, hides or reorders rows, it only puts break lines (section headers) between them.

  • /g/key1[,key2,...][/part...] - one section per distinct value of key1; a second key nests a sub-section inside each, and so on, outer first. Keys resolve like /sort keys (exact name wins, a fuzzy key expands to every type it reaches, alphabetically); a key that names nothing makes the whole /g inert. Only the last valid /g in a query takes effect.
  • Trailing parts, recognised by shape, in any order, each at most once: a bucket, a level (digits) and a direction (a prefix of ascending / descending; d is desc). Anything else makes the command inert.
  • Buckets (exact words). A bucket applies to the keys it fits; one that fits no key makes /g inert.
    • pf / parent-folder (path types): the folder holding the entry; level picks the ancestor: /g/path/pf/1 (the default) is the immediate parent, /g/path/pf/2 the one above it. pf and parent-folder also work as a key standing for the path type: /g/pf, /g/pf/2, /g/pf,dm/month. The level means nothing without pf (inert).
    • day | week | month | year (date types): /g/dm/week. Labels read Today, Yesterday, This week, Last week, This month, This year, else a date (2026-10-14, Week of 2026-10-12, September 2026). Weeks start on Monday.
    • No bucket: the default of the key's family, picked from its name - date types (date, modified, created, time, dm...) group by day; size by order of magnitude (< 1 KB, 1 - 10 KB ... 10 GB or more); age (5m, 3h) into Last hour / Last day / Last week / Last month / Older; path types by pf (level 1) - so /g/path is /g/path/pf/1; anything else by the exact value. A type whose name contains path holds the entry's full path, its own name included.
  • Order. With no direction typed, groups appear in the order their rows already have: the active /s, or the picker's default (newest first in mod+1, i.e. /s/dm/desc), so a group sits where its first row is. Exception, mod+1 only: pf (parent-folder) groups are folders, so they are ordered by the folder's own date modified (newest first; asc reverses), asked of the server's POST /mtimes; a folder the catalog has no date for falls back to its newest file. /g/key/asc or /g/key/desc instead sorts the groups by their key (newest day / biggest size / newest age bucket first for desc; text values Z-A for desc). The (none) group (empty or unparseable value) is always last. Rows inside a group keep the order the rest of the query gives them, so /g/dm/week /s/size is "per week, biggest first".
  • Sorting the sections themselves. A trailing s/key[/dir] (or sort/key[/dir]) part, once, orders the groups by an aggregate of key over all the rows in each (nested ones included), at every level; it replaces the key / folder-date ordering, and (none) stays last. /g/path/pf/1/s/size is "folders, biggest total first" (/s/size/asc the other way; direction defaults to descending, like /s). The aggregate follows the key's kind: size is the total bytes, a date type the newest value, count (always accepted) the number of rows, an all-integer type (pages) the sum, anything else its smallest value. A direction typed before the s part still belongs to the group key and is ignored while a section sort is present. This is separate from /s/size, which orders the rows inside the sections: /g/path/pf/1/s/size /s/size/desc does both. The parse result carries sort: {name, dir} (absent when not typed). A bare s, an unknown key or a second s part makes the /g inert.
  • Pipeline. Like /s, a /g token is position-independent, and it always acts on the result of the filters: /fv/name .rvt /g/dm/week and /g/dm/week /fv/name .rvt both group only the .rvt rows, counts are of surviving rows, and a group with no surviving rows does not exist. Order of the stages is fixed - rows -> filter -> sort -> group - whatever order they are typed in. A value token owned by //key or /fv/key is never read as a /g. A column verb (/ft /at /rt) cannot hide the grouped key's section: the headers come from the underlying value.
  • Collapse. Each section header can be folded by clicking it, or from the keyboard with the picker's fold key (mod+1: Ctrl+G, rebindable) on the selected row's section. State is held in memory per group id and reset when the query changes. A collapsed header keeps its count; the folded rows leave the sequence, so keyboard navigation skips them. Up / Down in a grouped grid keep the column and cross into the neighbouring section. A trailing collapse part (/g/extension/collapse, /g/dm/week/collapse, any position among the trailing parts, once) starts every section folded; clicking a header or the fold key then opens just that one. In the shared cores it is collapse: true on the parse result (absent when not typed); the QML pickers keep it as the "*" default in their fold map (groupInitial / groupToggle in dsl.js), mod+1 folds the sections of the first layout of each query (later live updates leave folds alone).
  • Rendering is each picker's own: a full-width header row with a break above it in the images grid, a header line between rows in list pickers. mod+1 asks the server for the first 20,000 matches (names, sizes, dates only), groups them locally and says grouped the first N of M when the result set is bigger; the thumbnails of the visible rows load lazily as before. A picker that does not group treats /g as inert.
  • Who honours it (2026-10-23): mod+1 (grid and list), alt-tab (winswitch), the clipboard and notification pickers, the app launcher, the RSS reader and the Claude usage panel fold into sections (header click or the fold key, Ctrl+G, on the selected row); the search CLI prints ## label [n] lines between the groups (--json: a "group" array per row; -0 and -c ignore it). The fzf pickers (focus-picker, window-search, claude-history) cannot fold a list into sections: /g is recognised there and ignored, never searched as text.
  • Tests: the group vectors in tests.json (parse / value / layout / visible / extract) run in Python, QML and Rust; test_dsl.py also runs the pipeline checks - every typing order of filter, sort and group gives the same rows and layout, counts only ever cover the rows the filters kept, an empty filter leaves no groups, and 300 random token mixes always cover each surviving row exactly once.
  • Shared code: parse_group, group_value, group_layout, group_visible, extract_group in ~/.config/dsl/dsl.py, ~/.config/quickshell/lib/dsl.js and ~/.config/dsl/group.rs, all proven by the group vectors in tests.json.

Quoting

"..." is checked first at every token position, so it is the universal escape hatch: a token that starts with " is never parsed as a command, and a literal / (or any other reserved character) inside quotes is just text. Beyond escaping, quoting lets a value or path segment span whitespace without splitting into separate tokens: //title "imperial rome", //app "discord canary".

A quoted value is matched as a literal contiguous substring, whitespace included, that must also stand alone (no letter/digit directly before or after it - see "Resolution, precisely") - //title "imp rom" matches only a title that actually contains the run imp rom, not "Imperial Rome". (This is a change from the older behaviour, where quoting meant subsequence-across- whitespace. Substring is now the single matching rule everywhere; "imperial rome" is what you type to match "Imperial Rome".) The BM25 pickers keep their own quoting meaning (required exact phrase) as noted above.

images picker. Quotes group words everywhere in the box, not only in values: "career essay" is one search term (a literal contiguous substring of the file name or path, and highlighted as one run), //name "tasks of" and //path "part 3" take the whole quoted run as their value, and /fts/part3-books daniel "career essay" passes the quoted run to Recoll as a phrase. /s and /sort inside quotes are plain text, never commands, and quoted runs keep their inner spacing when the order verbs are taken out of the query. An unterminated quote runs to the end of the box.

A //tag always owns the next token as its value, whatever that token looks like, so //path /etc filters on the path /etc and //path /sort on the text /sort; neither is read as a command. A / token that is not directly after a //tag (//path / /sort dm asc - the value is the lone /, then the sort) is parsed as usual. Photo (//clip, //face) queries are handled by the photo engine and do not group quoted words.

Syntax highlighting

Every search box that implements this DSL colours the commands in its own text, so you can see at a glance what the parser will treat as a command and what it will treat as plain text.

  • Painted: a token that the app's parser recognises as a command: an exact verb (/fv /ft /at /rt /s, plus an app's own such as /fts /clip /face), the /verb/via form, and a //tag default-verb form that names a real field. The leading ! of a negated command is not part of the command and stays plain.
  • Not painted: barewords, "quoted phrases", a //tag's value (it owns the next token whatever it looks like), and any /token that is not a command, such as the path /mnt/host1-backups/office. There is no "invalid command" colour: a token the parser would treat as plain text looks like plain text. A /token still being typed that might become a verb is also left plain.
  • How: the command is recoloured with the theme accent and set bold; the rest of the text keeps the normal text colour. It is the text itself, not an underline.
  • Colours come from the wallpaper palette. Apps read the generated Material You scheme (~/.local/state/quickshell/scheme.json, written by gen-theme.py): text is onSurface, commands are primary. Never hard-code a colour; a wallpaper change recolours the boxes.

Implementations: the Quickshell pickers share ~/.config/quickshell/theme/DslHighlight.qml (a transparent-text overlay inside the TextInput, fed the app's command spans; the input keeps the caret and selection). The images picker does it with an egui text layouter (command_spans / query_job in ~/bin/index/images/src/main.rs). Not yet done: the tmux TUIs (window-search, claude-history, focus-picker) and the Android app.

Autocompletion

2026-10-22 rework - current stages. Completion follows the single syntax of Grammar: (1) verb stage: / + Tab lists the five verbs, the app verbs, and every verb/key combination (Verb-stage depth); // + Tab is the key stage of /fv/. (2) key stage, after /verb/ and again after each ,: the type names, narrowed by the fragment after the last comma (accepting replaces just that fragment and keeps the typed verb spelling, // or /fv/). (3) direction stage, /s/keys/ + Tab: asc / desc. (4) value stage, after a resolved //keys : live values of the resolved types. There are no colon (path:value) or space-path (/s name ) stages any more; where older text below describes them, read the keys-in-the-token equivalent.

The popup is Tab-triggered to open, never shown just from typing. Nothing pops up on its own as you type /frag - typing alone only ever affects the row filter/columns/order the same way it always did. Pressing Tab is what asks "what could this become": if there's exactly one candidate, it completes immediately with no popup ever built or shown at all, the same way ordinary shell tab-completion silently completes an unambiguous path; only 2+ candidates actually reveal a popup, to choose among them. This applies uniformly everywhere: the QML consumers show/hide an overlay Rectangle, claude-history spawns/dismisses a nested fzf (see below) - always Tab-gated to open, never live. An always-on popup that repainted on every keystroke was tried first and dropped: it read as obtrusive, and once in a while it stole a focus/resize cycle at exactly the wrong moment.

Ctrl+Space also opens it, same as Tab. Landed first in clipboard-picker/notification-picker (2026-09-28), then ported everywhere else with a Tab-triggered popup at all, same day. A second way to ask "what could this become," bound to the closed-popup state specifically: once a popup is already open on a Verb-stage completion, Ctrl+Space instead AND-narrows it (see "Ctrl+Space AND-narrows a Verb-stage popup," below) - the same key does either job depending on whether there's already something open to narrow, never both at once. Implemented as one extra else if branch guarded on the popup being closed (!acPopup.visible/!ac.visible/!root.acOpen, picker to picker), calling the exact same completion-trigger function Tab's own closed-popup branch already calls - no new function, no grammar change, purely a second key reaching the same door. Landed in: ClipboardPicker.qml/ NotificationPicker.qml (Keys.onPressed, the reference implementation, both share the identical handler by hand, not by import); WinSwitch.qml (_triggerCompletion()); AppLauncher.qml (_triggerCompletion()); RssReader.qml (_triggerCompletion()); ClaudeUsageExpanded.qml (triggerCompletion(), no underscore - this file's own naming, unrelated to the feature). focus-picker and claude-history have no acOpen-style flag to gate on - their "popup" is a nested fzf process, not a QML Rectangle - so there the outer fzf's own --bind gains a second ctrl-space:execute(complete_cmd)+transform-query(...) line, byte-for-byte the same action tab:execute(...) already runs; the nested completion fzf's own ctrl-space:put( ) binding (its AND-narrowing) is untouched, since it's a different fzf process with a different query box. window-search stays out of scope, as it has no completion popup at all to extend (see the maturity note at the top of this section).

Once open, typing further narrows it instead of closing it (changed 2026-09-10 - the original rule closed the popup on the next keystroke, "the fragment it was built from is stale now, Tab recomputes fresh for wherever the cursor is"; reported as the wrong call once popups routinely held more than a handful of entries: /fv/ + Tab lists every field, and typing p should narrow that list to path/pid/... in place, not force another Tab press). Every keystroke while the popup is showing recomputes candidates fresh from the current text - the same computation Tab itself uses, just re-run on each change rather than gated behind the key - and replaces the shown rows with whatever comes back, resetting the highlight to the top: narrows as the fragment narrows, jumps to a whole new candidate set if the edit crosses into a different stage (finishing a type path and typing the value that follows it, say), and closes itself once nothing matches at all - the same "narrows to nothing" honest-empty-result rule the rest of the grammar already follows (see Design principles), not a special case. Unlike Tab's own trigger, narrowing down to exactly one candidate by typing never auto-accepts it - the popup still shows that one row and still waits for an explicit accept (Enter / Space / Tab - every picker accepts all three; Ctrl+Space is the AND-narrowing key, not accept), since silently applying a completion just because typing happened to narrow to a single match would be a surprise, not a convenience. Typing while nothing is open still never opens anything from scratch - that half of the original rule is unchanged, only the "once shown" half flipped from close-and-retrigger to narrow-in-place.

Typing / then pressing Tab is enough to discover the whole grammar (the list just won't appear until you actually press Tab - see above). All the QML pickers grow the same popup: an overlay under the search box (winswitch, the clipboard family, the app launcher, rss-reader, claude-usage); the two fzf pickers spawn a nested fzf instead. Stages:

  1. Verb (/frag, nothing after it yet): candidates are every short verb form whose name contains frag as a substring (/f -> /fv, /ft; / alone -> all of them), plus every verb/key combination (see Verb-stage depth). Accepting a bare verb inserts /verb/ (the keys part follows); accepting a deep candidate lands the whole command.
  2. Keys (/verb/frag, //frag, and again after each ,): candidates are the type names containing frag. Accepting one replaces just that fragment and keeps the typed spelling (// or /fv/); after /fv / // a trailing space is added (the value follows), after the other verbs nothing is (a , or /dir can follow).
  3. Direction (/s/keys/frag): candidates are asc / desc.
  4. Filter value (//keys frag, keys resolving to one type): every distinct non-empty value that type has across the current entries right now, substring-narrowed by frag, deduplicated and sorted. This is the one stage genuinely scoped to a small corpus.

An empty fragment lists everything for that stage, once Tab asks. /

  • Tab is every verb plus every verb/key combination the grammar can build (see Verb-stage depth, below); // / /fv/ + Tab is every type name; //keys + Tab is every value that type has. Discovery doesn't need a first character typed - just Tab, at any point - which is what makes "hidden until Tab" (above) fine for discoverability rather than a tradeoff against it.

Verb-stage depth

The Verb stage (stage 1, above) does not stop at the bare verbs: its candidate list is every verb plus every key-taking verb crossed with every type name it can take, rendered as the complete verb/key string (fv/workspace, s/tmux-session, at/claude-title, ...; the app verbs add their own, e.g. alt-tab's fts/claude, fts/claude-live, fts/claude-archive, fts/tmux). A fragment of the type, not just the verb, is therefore enough to reach a whole command: /wo + Tab reaches /fv/workspace, /ft/workspace, /at/workspace, /rt/workspace and /s/workspace, and /cla + Tab reaches every verb crossed with each claude-* type, narrowed by typing more (/claude-t keeps the types containing t).

Matching is the one rule everywhere: substr(fragment, candidate_text) against the complete verb/key string, so a fragment of either half reaches the same row. Accepting one inserts its full text and nothing else: /fv/workspace (a trailing space, the value follows) or /s/workspace (no space: a , or /dir can follow) - exactly what the same command parses to when typed by hand, so this adds completion candidates and changes nothing about the grammar. An empty fragment lists the whole vocabulary (/ + Tab).

The candidate list is computed from each picker's own type registry (winswitch's typeNames/allPaths, the clipboard family's fieldNames, the launcher's typeNames, ...), never hardcoded; a picker only crosses the verbs that do something there (the clipboard family and the launcher cross /fv and /s; claude-history crosses /fv; focus-picker also /at /rt /ft against its column names). Every picker with a completion popup implements it: the QML consumers in their _verbStageUniverse/verbStageUniverse, focus-picker and claude-history (nested fzf) in completion_stage/complete_query; window-search has no completion at all.

Row anatomy for a deep candidate (extends Suggestion row anatomy, below): label is the full /verb/key string; alias is the verb's own /long-form (/filter-value for an /fv/... row), as for a plain verb candidate; description is the type's one-liner (typeDescs: "the Hyprland workspace" for workspace), not the verb's - the type is the newer, less-obvious half once the verb is visible in the label.

Ctrl+Space AND-narrows a Verb-stage popup instead of accepting it. With the popup open on a "verb"-stage completion, Ctrl+Space inserts a literal space and keeps the popup open, rather than accepting the highlighted row the way plain Space does (see Suggestion row anatomy, below, for Space's ordinary meaning) - so /wo + Tab (five rows: every verb crossed with workspace) + Ctrl+Space + fv narrows that same five down to just /fv/workspace, the one row whose full verb/path text contains both wo and fv. Each fragment (space-separated, including the one the popup was already open on) must independently substring-match a candidate's complete text - an AND over the fragments, not a second, narrower substring search - so fragment order never matters and a third Ctrl+Space narrows further the same way a second one does. Every other popup (type-path, value, bare value, sort direction) narrows the same way since 2026-10-21: //cla + Tab + Ctrl+Space + tit keeps only candidates containing both cla and tit (claude-title). The first word is still the real completion fragment (so the candidate set is whatever cla completes to); each further word must also substring-match the candidate's text. Accept replaces from the frozen fragment start, same as the Verb stage. Implemented in winswitch (acArgMulti), the ClipboardQueryDsl family (_argMulti: clipboard, notification, revit-remote, appmenu) and the launcher / rss-reader / claude-usage panel (acArgMulti, re-entering _acCandidates with the first word). Not applied to the Verb stage, which has its own universe-wide AND (above). No-op, not a grammar change, either - the text that ends up typed (/wo fv) is never itself parsed as two tokens the way plain typing normally would be (that would make wo a literal /fv text search once a space followed it, since wo isn't a prefix of any verb - see Design principles' "never flash to zero"): the popup intercepts recomputation while this mode is active and replaces the whole span from the completion's original opening / through the cursor in one go on accept, the same as accepting any other Verb-stage row already does.

Same rollout as Verb-stage depth, same day: winswitch first (WinSwitch.qml's acVerbMulti/acVerbMultiStart), then each other QML consumer (the clipboard family, app-launcher, rss-reader, claude-usage).

The fzf-native completion popup (focus-picker, claude-history) picked this up 2026-09-13, once it had a real popup at all (see Verb-stage depth's own rollout note, above) - Ctrl+Space is bound there to fzf's own put( ) action (insert a literal space into fzf's own query box, without accepting), the same functional outcome as the GTK/QML families' custom AND-narrowing logic, but for a structurally different reason: this popup has no separate "Space accepts" rule to work around in the first place (Enter/Tab accept here, plain Space does fzf's own ordinary thing - typing a literal character - see Shared popup UI, below, for why this family never got the other two's "Space also accepts" convention), so plain Space already inserts a literal space and narrows same as Ctrl+Space would; the binding exists anyway so the key matches winswitch's, not because the space needed rescuing from an accept binding. The AND-narrowing itself needs no DSL code either: this popup runs fzf's own untouched fuzzy matcher already (see Search-box history, below, for why that's deliberate here and not the grammar's usual substring rule), which already ANDs space-separated fragments together natively - typing a second fragment after any space, Ctrl+Space-typed or not, was already narrowing further before this change; put( ) only adds the specific keystroke. Not scoped to a "Verb stage" the way winswitch's is, either - this popup only ever shows one flat candidate list per Tab press (Verb-stage depth already flattens verb and path together into one popup - see above), so there's no separate stage for it to be inert in. window-search has no completion popup at all to extend this into (see the maturity note at the top of Autocompletion).

Auto-shown filter fields

A type actively scoped by a filter (//claude-title ovh, /fv/claude ovh) is shown even without an explicit /at - and even past an /ft//rt that would otherwise hide it - so the value that actually matched is visible whenever more than one candidate is left to choose between, rather than a filter narrowing the result set for reasons that aren't on screen. This is additive to whatever /ft//at//rt computed (or, in a picker with no column system, to its fixed default display) - never a replacement - and it disappears the moment the scoping term is deleted.

It triggers the moment the keys are named, not just once a value narrows anything. //claude-session with no value yet (about to add one) already resolves its keys to real types; that stays a no-op for row filtering ("never flash to zero on a partial keystroke", Design principles) but Auto-show reads the same resolution and shows the column at once. A key list that resolves to nothing (a typo, a fragment on its way to a name) shows nothing, exactly as it does for a complete term. An empty keys part is nothing typed yet: // or /fv/ must not resolve at all - an empty substring matches every type name, and the union rule a fuzzy key legitimately gets (//cl reaching every type containing cl) would auto-show every column at once (reported 2026-09-13). Each implementation guards the early trigger on a non-empty key list (keys.replace(/,/g, "").length > 0).

What "shown" means is picker-specific:

  • winswitch: the referenced types become active columns exactly like an /at (WinSwitchQueryDsl.qml's filterReferencedFields, folded into activeColumns), rendered as one extra line each under the thumbnail (WinSwitch.qml's labelLines); the grid's cells grow (labelAllowance) to fit.
  • clipboard / notification / revit-remote / appmenu pickers: a dim extra line under the entry's preview (ClipboardPicker.qml and siblings, over ClipboardQueryDsl.referencedFields) - these have no real column system.
  • app-launcher / rss-reader: a dim second (RSS: third) line under the app name / article title, skipping fields the row already shows unconditionally.
  • claude-usage: a no-op - its table already renders every type as a column (/ft /at /rt are inert there).

Auto-show is implemented in the QML consumers only; window-search, focus-picker and claude-history have no extra-line rendering to feed.

A family type's auto-shown line is labelled with its own name, and gated per row when the key reached several types. Types of a family share a hyphenated prefix (claude-title, claude-path, ...), and a fuzzy key (//claude ovh) reaches all of them, so which type actually matched differs row to row. In winswitch:

  • Labelling. A family type's line renders as sub: value (title: ovh proposal draft) rather than a bare value; the reader cannot otherwise tell which type they are looking at. This applies to every such line, including one added with /at/claude.
  • Per-row gating. A type reached through a multi-type scoped filter is shown only on rows where it is the one that matched; a type shown for any other reason (/at, a key naming exactly one type) is always shown once it has a non-empty value.
  • Match-centred preview. The shown value is capped (80 chars), and when the line is tied to a matched filter value the window is centred on the match's first occurrence instead of starting at character 0 - the first 80 characters of a long field rarely contain the matched substring, so the preview read as unrelated noise even on a correct match. Types not tied to a matched value keep plain start-truncation.

WinSwitchQueryDsl.qml's scopedGroupFilters (the {group, value} pairs for multi-type keys) and excerpt (the centring helper) are the reference; WinSwitch.qml's labelLines applies both per row.

Suggestion row anatomy

Each row is three fields, left to right, in the style of emacs marginalia / zsh's completion descriptions:

/ft   (/filter-type)   show only the matching columns
└─┬─  └──────┬──────┘   └──────────────┬─────────────┘
 what      the long-form alias,        a one-line description
 accepting  greyed - a hint that       of what the verb does,
 inserts    /ft *is* /filter-type,     also greyed
            not a second command
  • Verb stage: label is the short form; the alias is its /long-form in parens, greyed; the description is the verb's one-liner (below).
  • Type-path stage: label is the type (or group) name; no alias; the description is what that field/group is in this picker (e.g. title -> "the window title", claude -> "Claude Code session metadata"). A picker with no per-field blurbs may leave the description empty.
  • Value / direction stages: label only; these are concrete data, not grammar, so there's nothing to describe.

Only the alias and description are greyed; the label itself takes the normal / selected-row colour. A picker that can't render three columns (the BM25 single-line pickers) shows the label alone.

Verb one-liners (keep these consistent across implementations - the quickshell launcher reads them from QueryDsl.qml's verbInfo):

Verb Alias Description
/fv /filter-value keep rows whose value matches (substring)
/ft /filter-type show only the matching columns
/at /add-type add the matching columns
/rt /remove-type drop the matching columns
/s /sort order rows by one field, optional asc / desc

Shared popup UI: Tab triggers completion when nothing's open yet (see above - unique candidate applies directly, 2+ opens the popup). Once the popup is open, Tab confirms the highlighted suggestion, the same as Enter (changed 2026-10-16: it used to move the highlight down in the QML and fzf-native families, which made Tab behave differently per picker; it now means "accept" everywhere, the AutoCAD-style convention Space already followed). Moving the highlight is Down/Up (and Ctrl+j/Ctrl+k where bound), Shift+Tab steps it back; none of those accept. Per family:

  • QML pickers (app-launcher, rss-reader, claude-usage, winswitch, clipboard/notification/revit-remote pickers): Tab accepts; Shift+Tab steps the highlight back (wrapping); Down/Up (and, in app-launcher/ winswitch, Ctrl+j/Ctrl+k) move it, clamped. winswitch's Alt+Tab while locked into search mode is the one place Tab still cycles the highlight (a chord, so it can't be mistaken for a plain accept).
  • Clipboard-family pickers (ClipboardQueryDsl.qml): Tab accepts outright; Ctrl+j/Ctrl+k move the highlight (clamped, not wrapped).

Space accepts the highlighted suggestion everywhere the popup is open, in both families, alongside whichever of Tab/Enter already did (added 2026-09-10 - the AutoCAD convention of the spacebar confirming the current command/entry). It's consumed only while the popup is showing; with no popup open, Space types a literal space into the query exactly as it always did.

  • fzf-native pickers (focus-picker, claude-history - a nested fzf process, not an in-layout widget the picker itself draws and can rebind at will): the nested complete> / history> fzf is launched with --bind tab:accept, so Tab accepts like Enter; Down/Up move the highlight and Space types a literal space into fzf's own query box (never repurposed to accept: this family has no "Space also accepts" rule - accepting is already one keystroke away, and Space narrowing further is what Ctrl+Space AND-narrowing, above, builds on directly).

Escape dismisses just the popup, never the picker. In a picker where Tab already meant something else while nothing's open (clipboard-picker/notification-picker's and the RSS reader's search-list focus toggle), completion only claims the key when it actually found a candidate - a bare Tab with nothing to complete falls through to that other meaning unchanged, it doesn't just eat the keypress. One bug worth remembering if the popup ever silently stops appearing: a GtkListBox built with no-show-all (so the picker's one-time startup show_all() doesn't reveal an empty popup) also ignores a later show_all() meant to reveal it - every row/label has to be shown explicitly and the list revealed with a direct .show().

Inline command-validity coloring. As a command is typed, the whole /verb (or /verb/via, or //via) token is colored to show whether it currently resolves to a real command, not left in the query's ordinary text color: one color once it's a recognized verb, a distinctly different one while it isn't (an unrecognized verb, or a genuinely-wrong-looking /xyz that isn't even a prefix of one) - the same at-a-glance "is this valid" a shell's own syntax highlighting already gives a command name. A still-forming prefix of a real verb (typing /f on the way to /fv) stays neutral - not wrong yet, just incomplete - rather than flashing the invalid color on every keystroke. Scoped to verb-name validity only: /fv/bogus_field still colors as valid, because an unresolved via isn't necessarily a mistake (/ft's via falls back to a legitimate value pattern when it doesn't resolve as a path - see above - so "did the via resolve" isn't a reliable valid/invalid signal the way "is this a real verb" is). This is presentation only and never changes matching or resolution - a "wrong" color is exactly what is_verb_prefix/ Verb::parse (or a picker's own equivalent) already says is unresolved, nothing new to compute, just something new to render the answer with. commandSpans (in WinSwitchQueryDsl.qml, ClipboardQueryDsl.qml and each launcher-style consumer's _commandSpans) is the one function that answers it, from a token list identical to what starts_command/ tok_verb already tokenize the query into.

Never hardcode either color - both come from whatever dynamic theme source the app already has, since this desktop regenerates its whole palette from the wallpaper (gen-theme.py); a color baked into a picker's source would just go stale the next regeneration, or clash outright. the QML consumers read the generated Theme colours (from ~/.local/state/quickshell/ scheme.json) - its primary/ error keys are the valid/invalid pair here (not secondary: this theme's secondary sits too close in hue to primary to read as a distinct "wrong" signal, where error is a deliberately different one - check the live values before picking a role, don't assume the name alone); the QML consumers already have a Theme singleton fed from the same generated file (Theme.cyan / Theme.red map to those same two roles). Which specific role name means "valid" vs "invalid" is still each app's own call in principle - the DSL only cares that the two stay visually distinct and both move when the theme does, never that they're any particular hex value.

(The GTK implementation could recolour glyph ranges with Pango attributes; that is gone with GTK.) QtQuick's plain TextInput has no equivalent (no per-range rich-text styling), and recoloring the whole input would falsely tint bare filter words alongside the command - so the QML consumers draw a thin colored underline under just the command span instead, positioned via TextInput.positionToRectangle (which stays correct once the field scrolls, unlike computing an x-offset by hand with TextMetrics) rather than recoloring the glyphs themselves. The three fzf-driven pickers (window-search, claude-history, focus-picker) don't have this at all yet: fzf owns and renders its own query line with no hook for a script to recolor it live per keystroke, so there's no direct equivalent of either technique above - the closest fzf-native analogue would be a colored validity hint folded into a dynamically-redrawn header (the way focus-picker's [tab → x] hint already works), which is a materially different mechanism and hasn't been built.

Per-picker autocomplete scope. A picker only offers the verbs that do something for it. The app launcher shows no columns, so it offers /fv, /s only - /ft//at//rt are still parsed (shared grammar) but inert, so they're left out of the popup rather than suggested and then ignored. claude-history only acts on /fv at all (see its own header), so its Tab-completion only ever offers that - the verb stage lists fv/filter-value and nothing else, and only via paths get completed (/fv/field value, steering towards that spelling specifically even though the older colon spelling is gone). Its completion UI can't be an in-layout popup the GTK pickers' way (fzf has one list, not a widget tree) - a unique candidate completes directly, the same way shell tab-completion does with no ambiguity to show; an ambiguous one opens a small nested fzf as the actual picker, launched via execute(...) (which hands the terminal over to it, same as fzf's own execute(less {})) and fed back into the query with transform-query(...) once you pick one.

Search-box history (Up-arrow, Ctrl+R)

Two bindings, modeled directly on zsh's own line editor plus this user's fzf ctrl-r widget (~/.zshrc's _fzf_history_widget_wrapper, plain fzf-history-widget underneath - its only customization is where the popup renders, --tmux placement, never how it matches or orders), so the shell muscle memory transfers straight into every picker's search box with no new mechanism to learn.

  • Up-arrow cycles the search box's whole text backward through that picker's own previously-submitted queries, most-recent-first - the same job zsh's default up-line-or-history binding does. Down-arrow walks forward again, symmetric with Up, eventually landing back on whatever was actually being typed before the first Up press (the pre-cycle draft, restored verbatim, even if it was empty) rather than getting stuck on the oldest entry once you've walked past it - zsh does the same. Scoped to whenever the search box is focused and no popup (completion or history) is currently open - both because Up/Down are already claimed for moving the completion popup's highlight once one is open (QML pickers: Down/Up move it, clamped - see Shared popup UI, above), and because replacing the box's text out from under an open completion popup that's narrowed to the old text would be actively confusing. The fzf-native pickers give up Up/Down as row-navigation entirely to make room for this (there's no separate "popup" state to scope around there the way there is for a QML completion overlay - Up/Down are the main list's own navigation by default) - row navigation moves to ctrl-j/ctrl-k instead, which cost nothing new to bind since they're already fzf's own default synonyms for down/up.

  • Ctrl+K / Ctrl+J are Up / Down in the search box (added 2026-10-21), wherever Up/Down are history: Ctrl+K cycles back through past entries exactly like Up and so starts a history walk. Ctrl+J is Down, which has two meanings: while a walk is on (an Up/Ctrl+K press has happened and the pre-cycle draft hasn't been restored yet) it steps forward through history; otherwise it is not history at all and does what plain Down does in that picker - move on into the results (focus the list / the second entry below the already-selected first one, per Focus between search box and results, below). So Ctrl+J never starts a walk and never replays an entry from a cold box. With a completion/history popup open Ctrl+J/K keep moving its highlight, and with the results focused they navigate rows as before. Consequence: in the pickers with history, row navigation back up from the search box is no longer Ctrl+K (it is history now), same as Up. Implemented in app-launcher, winswitch, rss-reader, claude-usage (Ctrl+J/K branches next to the Down/Up ones), images (kb_up/kb_down in main.rs), and focus-picker / claude-history via ~/bin/fzf-histnav (fzf transform: keeps a depth counter + the query history last put in the box, so Down/Ctrl+J only step history forward while the box still holds it; all four of Up/Ctrl+K/Down/Ctrl+J bind to it, and Down with no walk moves the fzf list down and records the query as before). Pickers with no search-box history (clipboard, notification, app-menu, revit-remote, window-search) are unchanged: Ctrl+J/K stay plain row navigation.

  • The Ctrl+R popup closes once an entry is chosen (all pickers), and is never carried across a close/reopen of the window. Choosing an entry (Enter/Tab/click) replaces the whole query and ends the popup - unlike a Tab-completion popup, which stays open and re-narrows after accepting a stage, there is nothing further to complete in a finished query. Implementations close the popup before writing the text, or the text-change recompute reopens it (app-launcher, rss-reader, claude-usage); winswitch and images already did; the fzf pickers' nested popup exits on accept by construction.

  • Ctrl+R opens a popup - the same shared popup machinery Tab-completion already uses (nested fzf for the fzf-native pickers, in-layout GtkListBox/QML overlay elsewhere - see Autocompletion, above), but pointed at a different corpus and a different matcher:

    • Corpus: the picker's own history list, most-recent-first, same list Up-arrow cycles through - not the DSL's verb/type/value candidates.
    • Matcher: fzf's own default fuzzy algorithm, not this DSL's plain substring rule (Resolution, precisely, below) - a deliberate second exception to "no subsequence matching anywhere" (the first being /ft's glob-pattern fallback), made because the whole point of this binding is reusing zsh ctrl-r muscle memory, not staying internally consistent with the rest of the grammar. This is free for the three fzf-native pickers: the nested completion fzf already runs with fzf's untouched default matcher (no --disabled, no --exact - only the outer fzf runs --disabled, to hand filtering to the DSL), so pointing that exact same nested-fzf plumbing at the history file instead of the candidate list needs no new matching code, only a new corpus and a new trigger key. Non-fzf pickers approximate the same feel with a fuzzy/subsequence scorer in their own popup instead of substring, since there's no nested fzf to borrow one from.
    • Seed: the popup opens pre-filtered by whatever's currently in the search box (fzf --query "$LBUFFER"'s own behavior), not empty - then narrows further exactly like a Tab-completion popup already does on every keystroke (recompute-in-place, reset highlight to top, close on zero matches - see Autocompletion, above; nothing new to invent here either).
    • Accept (Enter - the fzf-native family's own accept key, see Shared popup UI's fzf-native bullet, above; not Space/Tab, which do fzf's own ordinary things in this popup too) replaces the entire search-box text with the chosen history entry, cursor at the end - a whole-line replace, not an insert at cursor, matching zsh's own LBUFFER=$selected. The caret must really be parked at the end of the inserted text (not left where it was, or at the start) in every picker, so typing carries on from the end of the recalled query.
    • Escape dismisses just the popup, search box left exactly as it was before Ctrl+R was pressed - same as every other popup in this DSL.

  • Inline suggestion (zsh-autosuggestions). While typing, the rest of the newest history entry that starts with the text typed so far (case-sensitive prefix, strictly longer than the text) is drawn in greyed-out text directly after the cursor, from the same history list Up-arrow and Ctrl+R use. Right-arrow, End or Ctrl+F accepts it (appends the greyed text and parks the cursor at the end); anything else typed just narrows or drops it. Shown only when the cursor is at the end of a non-blank search box and no popup (completion or history) is open; Shift+arrow and a cursor mid-text never take it, so Right/End keep their ordinary editing meaning whenever there is no suggestion. Nothing is recorded by accepting it (history is only written on accept / selection-move, as above). Landed 2026-10-11 in the images picker (egui) and the four QML pickers (app-launcher, winswitch, rss-reader, claude-usage), each via a suggest(text) helper on its history store. The fzf-native pickers (focus-picker, claude-history) cannot draw ghost text inside fzf's query line, so they are out of scope; clipboard-, notification- and revit-remote pickers have no search-box history yet, so no suggestion either.

What gets recorded, and when. A query is appended to that picker's own history the moment the user acts on it in the results grid - not on every keystroke, and not while a query is only still being typed. Two things count as "acted on," added 2026-09-13 after the first cut (accept only) turned out to be too narrow in practice: an actual accept (Enter activating a row - the shell analogue, "a command" being whatever was run) and, separately, moving the row selection after typing (arrow/ctrl-j/ ctrl-k navigating the results without ever accepting one) - browsing a query's results is itself evidence the query was finished and useful, even if the session ends without jumping anywhere. Neither fires mid-typing: a keystroke that only changes the query text itself is never on its own a trigger, only what comes after typing pauses - so a query still being composed never gets a half-typed fragment recorded (this DSL's own "never flash to zero on a valid partial keystroke" spirit, applied to history instead of results - see Design principles, below). An empty search box at either moment records nothing (a shell doesn't journal a blank line either). Whitespace runs are collapsed to one space before storing or comparing (mirrors this user's HIST_REDUCE_BLANKS), and a submitted query identical, after that normalization, to an existing entry anywhere in history removes the older occurrence and re-appends fresh at the end instead of growing a duplicate - mirrors HIST_IGNORE_ALL_DUPS, which this user's .zshrc already sets, so a query typed a third time floats back to "most recent" instead of piling up three near-identical rows in the Ctrl+R popup.

One history list per picker, not shared across them. Same reasoning the doc already gives for field/group vocabularies not needing to match picker to picker (The shape of it, above): each picker's queries are shaped by, and only meaningful against, that picker's own corpus and type vocabulary - a claude-title scope typed in claude-usage means nothing replayed into window-search. Stored per picker under its own cache directory (mirroring ~/.zsh_history itself - one file per shell, not a merged global one), unbounded, like this user's own HISTSIZE=99999999/SAVEHIST, rather than capped and pruned.

Written immediately, read fresh on every Ctrl+R - not just cached at picker startup. Mirrors INC_APPEND_HISTORY + SHARE_HISTORY: a one-shot fzf-native picker (window-search, focus-picker, claude-history) is a fresh process every invocation anyway, so this is automatic there - there's no earlier in-memory snapshot to go stale. It matters more for the long-lived QML/GTK pickers - the quickshell shell process and its panels stay resident across many separate open/close cycles, unlike a shell that exits with its terminal - so each of those should re-read its history file at the moment Ctrl+R opens the popup rather than rely on whatever it loaded once at qs startup, so a query submitted in one open-close cycle is visible to Ctrl+R the very next time that same picker is opened, the same way a second concurrent zsh session sees a first session's just-run command under SHARE_HISTORY.

Out of scope: claude-agents (Android). No physical Up-arrow or Ctrl+R exists on a phone keyboard, and its QueryDsl.kt already departs from the desktop completion model for the same reason (live-as-you-type, no Tab-gating - see the table entry above); a touch-native equivalent (e.g. a swipe-to-recall gesture, or a persistent "recent searches" chip row) would be its own design, not a port of this section, and hasn't been asked for.

Rollout: focus-picker and claude-history, 2026-09-13; the rest not yet built. Landed first in the two fzf-native tmux pickers, where it turned out to need almost no new mechanism: fzf's own --history=FILE flag already is Up-arrow-style cycling (confirmed directly, a scripted expect session against real fzf - loads oldest-first, writes the file only on a genuine accept, never on Escape/ctrl-c, and restores the pre-cycle draft verbatim once you walk forward past the newest entry - every part of the Up-arrow bullet above, for free). Bound to the literal up/down actions (--bind up:prev-history --bind down:next-history), not fzf's own ctrl-p/ctrl-n auto-remap default, since real usage showed that's what "Up-arrow" actually needs to mean here - row navigation moves to ctrl-j/ctrl-k instead (see the Up-arrow bullet's own note on this). dedupe_history() (focus-picker.py, claude-history) is the one thing fzf's flag doesn't do on its own - it appends unconditionally, no HIST_IGNORE_ALL_DUPS equivalent - so both run it right after the outer fzf exits, collapsing the file to last-occurrence-wins order before the next invocation's --history load or this invocation's own Ctrl+R popup ever reads it. The "moving the selection also records" half of "What gets recorded, and when" (above) is ctrl-j/ctrl-k's own execute-silent bind, appending the live query with no read-modify-write (record_history() in focus-picker.py; history_candidates()'s sibling record mode + socket handler in claude-history) - left as a raw, undeduped append on every nav keystroke rather than a full read-dedupe- write each time, since dedupe_history() already cleans it up once at exit and a same-session Ctrl+R seeing a few repeats of one line in the meantime is cosmetic, not a correctness problem. Ctrl+R (history_search() in focus-picker.py; history_candidates() + CLIENT_SRC's new history mode in claude-history) reuses the exact same execute()+transform-query() nested-fzf plumbing Tab-completion already had, pointed at the history file instead of the DSL candidate list, with one behavioral difference from Tab: it always opens the popup (zsh's own ctrl-r widget does too, unconditionally) rather than Tab's "a unique candidate completes silently" rule, since Ctrl+R's whole point is browsing, not narrowing to an obvious single answer. window-search stays out of scope for the same reason it already sits out of the rest of Autocompletion (see the maturity note at the top of this document).

Focus between search box and results (Down / Tab)

Added 2026-10-21 (alt+tab, rss-reader, claude-usage, app-launcher). One rule for every picker that has a search box above a results area, whatever the results look like (thumbnail grid, article list, schedule, plain rows):

  • Down in the search box moves focus into the results, when no completion/history popup is open and the box is not mid-history-cycle. With a popup open Down still moves its highlight; while cycling history (an Up press has happened and the draft hasn't been restored yet) Down still walks history forward (see Search-box history, above) - so the first Down after typing, or after cycling back to the draft, leaves the box. The query text is left exactly as typed.
  • Tab in the results returns focus to the search box (cursor at the end of the query). Tab inside the search box is unchanged: it is completion (see Autocompletion); where completion has nothing to offer and the picker already had a list-focus mode (rss-reader) it falls through to the same toggle.
  • Typing a printable character while the results have focus returns to the search box and appends it (alt+tab). Escape keeps its usual meaning (close the picker); Enter acts on the selection.
  • While results have focus, the picker's bare-key navigation (arrows, Ctrl+J/K, j/k where the list has them) applies as in an unlocked view.
  • Single-focus pickers (query entry never loses focus; row navigation is Up/Down or Ctrl+J/K on top of it: clipboard, notification, app-menu, revit-remote pickers, and the fzf TUIs) have no separate results focus to move to, so the rule degrades to: Down walks the results (app-launcher gained this: it used to be dead unless history-cycling). They need no Tab-back.
  • Up is not history once you have walked the results (2026-10-21). Up/Ctrl+K is history only from a cold box. After Down/Ctrl+J has moved the selection from the search box (single-focus pickers: app-launcher, claude-history, focus-picker), Up/Ctrl+K moves it back up the results; when it is back on the first row the next Up starts history as usual. Any edit of the query ends the walk. Where the results have their own focus (alt+tab, rss-reader, claude-usage, images) Up/Ctrl+K already navigate rows there, and the table views (/fts/archive) take the same focus hand-over as the grid. fzf TUIs: ~/bin/fzf-histnav remembers the query at the Down that walked the list ($state.walked) and uses $FZF_POS to know when the first row is reached.

Per implementation: winswitch/WinSwitch.qml (listFocused, _focusList()/_focusSearch(); unlocked Alt+Tab cycling is untouched - Tab still advances there), rssreader/RssReader.qml (_returnFocusToList(), existing Tab toggle), bar/ClaudeUsageExpanded.qml (Down hands focus to the panel's row selection, Tab in Bar.qml brings it back), launcher/AppLauncher.qml (single-focus form). Not yet live-tested.

Resolution, precisely

  • Verb: exact match against the fixed spellings (fv ft at rt s and their long forms, plus an app's own such as fts/sw, plus the empty //). Nothing else.
  • Keys: per key, the type named exactly wins alone, else every type whose name contains it (case-insensitive substring); unioned across the comma list. A sort key expands the same way, alphabetically. Filter values: substring containment ("rome" in value). Direction: any non-empty prefix of ascending / descending.
  • Quoted values stand alone: a value in "double" or 'single' quotes (bare, or a scoped value //path "5") must not touch a letter, digit or underscore on either side, so "5" matches 5 but not 15 or 599, and "rome" matches "Rome wasn't" but not "Romeo". Unquoted 5 is the ordinary substring and matches 599 too. A ' only opens a quote at the start of a token, so apostrophes inside words (don't) stay plain text. The quote must be closed: while only the opening quote is typed ("5) the term is still an ordinary substring, and becomes exact when the closing quote lands.
  • BM25 pickers' bare words: prefix-expansion against the corpus vocabulary, BM25-scored - their own thing, on top of the above.

No subsequence matching anywhere anymore (it was the old winswitch/GTK rule - "crit" matching "alacritty"). Substring is stricter and more predictable, and at these corpus sizes the looseness bought nothing.

Design principles

  • Never flash to zero results on a valid-so-far partial keystroke. A token still being typed (/, /f, /ft , /ft cla, /s age , a flat-type /fv/path with no value yet, an unterminated "phrase) is inert - contributes no requirement - rather than searched for literally as typed. A bare / (the empty string as the verb-name fragment) is the boundary case here worth calling out explicitly: every verb form trivially "starts with" the empty string, so is_verb_prefix/ isVerbPrefix needs no special-casing to cover it - a guard excluding the empty string (!s.is_empty(), s.length > 0, bool(s)) looks like reasonable defensive code but actively reintroduces this exact regression, since it makes the very first keystroke of any command fall through as literal text instead of staying inert. Reported 2026-09-13 against winswitch (typing / alone cleared the whole grid) and found identically broken in every hand-written port that had this guard (QueryDsl.qml, ClipboardQueryDsl.qml, the old picker.rs, focus-picker.py) - window-search.py and claude-history are naturally immune, since their regex-based bare-word fallback tokenizes / down to zero alphanumeric characters and contributes nothing on its own.
  • Every picker keeps one plain-typing default with no syntax at all. Bare text is always /filter-value over the free-text haystack. The DSL is additive, never a wall a casual user has to learn first.
  • /filter-value is the universal fallback, not just the no-syntax default. Every verb has a fixed arity (max tokens it consumes, /sort's direction slot additionally conditional on resolving); a token beyond what the preceding verb actually needed is never swallowed into that command just because no new /verb intervened - it resumes as an ordinary token and, if nothing else claims it, becomes its own /fv term. /s/name blender sorts by name and filters to blender, rather than losing blender as a discarded sort-direction argument.
  • Verbs are a closed, exact-matched vocabulary. This is the point of the redesign - a command can never be confused for a type name.
  • No real regex anywhere. Every match is substring containment (or, in the BM25 pickers, prefix-expansion); the only * is /ft's value-pattern glob (/ft/64*), a hand-parsed pattern, not a wildcard engine.
  • The three axes are orthogonal. Row filters (/fv, bare text) never change columns; column verbs (/ft, /at, /rt) never change which rows survive; order verbs (/sort) never change either.
  • Column verbs are a left-to-right pipeline; row filters are an order-independent AND; /sort is last-wins.
  • Quoting is the universal escape hatch, checked before every other grammar form.
  • An unresolvable complete path narrows to nothing (honest empty result) rather than degrading to a literal text search - these corpora are small and unranked enough that "matches nothing" is the clearer answer. (The BM25 pickers, being ranked, still degrade a typo'd scoped term to a plain ranked search.)
  • Selection follows the user, not the query - where there's no reason for it to follow something else. clipboard-picker / notification- picker open with nothing selected; the first navigation selects the top visible entry; a selection filtered out of view is cleared. Enter with nothing selected activates the top visible entry. winswitch's grid is the deliberate exception - it auto-selects on open, because landing on the previously active window the instant a single Alt+Tab tap completes is the whole point of alt-tab.

Full-text search over Claude conversations: one engine (2026-10-21)

One source for every consumer: a Recoll/Xapian index of Claude conversations, ~/.cache/indexes/claude/recoll, a collection like the others under ~/.cache/indexes/ (not registered in photos.json's fts.indexes, so mod+1's /fts doesn't search it). ~/bin/claude-fts-index (claude-fts-index.timer, every 2 min) writes ~/.cache/indexes/claude/sessions/<session-id>.txt for each transcript of every ~/.claude* profile - whole history, AI title first line, then user + assistant text blocks only - re-extracting only changed transcripts, then runs recollindex (which re-reads only changed files).

claude-history --fts QUERY is the single query entry (recollq underneath): prints session_id<TAB>relevance%, best first. !word -> -word, "phrases" as is, the last bare word matches as a prefix (live typing).

  • tmux picker (prefix+C-c): bare words, "phrases" and !neg are plain substring filters over the table's own values (tmux location, time, path, title); full text only through /fts word (one word or one "quoted phrase" per /fts; repeat it to AND more) or /fv/body. The preview pane is hidden until /fts is in the query.
  • alt-tab: /fts[/claude] term, see the scopes below.
  • Claude usage panel (ctrl+alt+c): /fts term; with no explicit sort, rows order by relevance.

Alt-tab and the usage panel show a match-preview strip (excerpts of the highlighted entry's conversation around the searched words, from claude-history --snippets SESSION QUERY) only while a full-text term is in the query.

/fts - live and archived conversations (2026-10-22)

The index holds every conversation; which ones are running is decided at query time (sessions registry), not stored in it. /fts is an app verb whose keys name the scope: the scope names are claude-live, claude-archive and tmux (scrollback, below), resolved like any other keys (exact name wins, else substring, comma list unioned):

Spelling Searches Rows
/fts word running, archived AND tmux scrollback (no keys = every scope) live rows first-class, archived and tmux ones appended (best match first)
/fts/claude word the same (claude reaches both scope names)
/fts/live word (= /fts/claude-live) running only live rows
/fts/archive [word] (= /fts/claude-archive) past only (running ones excluded); without a word, newest first table: acct, title, msgs, tkns, age, path
/fts/tmux word tmux scrollback only one row per matching pane (status tmux)

So live, archive, claude-live, arch, tmux all work (any key that reaches exactly one scope name); a key set that reaches both - or /fts/live,archive

  • is plain /fts. Writing both /fts/live and /fts/archive is plain /fts too. The same spellings are used everywhere (picker, panel, alt-tab). The verb is still exact (/fts); only its keys are fuzzy.

Per implementation:

  • prefix+C-c: default (no /fts) lists the running sessions in the panel's columns (ACCT STATUS TITLE MSGS TKNS AGE SESS WIN PANE WKS PID PATH), Enter jumps to the pane. /fts word adds archived hits to the same table (their live-only cells blank; Enter resumes them in a new tmux window under their own account). /fts/archive swaps to the shorter archive columns.
  • ctrl+alt+c panel: same: /fts word appends archived rows after the live matches; /fts/archive drops the columns that only exist for a running session (status, tmux sess/win/pane, workspace, pid). Enter/click on an archived row resumes it.
  • alt-tab: /fts/live word keeps the window grid, filtered; /fts/archive and plain /fts word replace the grid by a table (live rows marked ●; Enter focuses the window, on an archived row resumes it). The table keeps the grid's height.

Resuming (claude-history --resume-window for the panel and alt-tab: a new tmux session in the session's cwd, labelled with the account, attached in a new alacritty window; prefix+C-c: --resume-tmux, a new tmux window) always uses the account the conversation last ran under.

Not to be confused with the images picker's /fts/<index> (file contents, index name after the slash): different app, different corpus.

tmux scrollback in /fts (2026-10-22)

claude-fts-index (the same timer/daemon that keeps the conversation index) also indexes the scrollback of every tmux pane into a second, separate Xapian database, ~/.cache/indexes/tmux/recoll (one .txt per pane in ~/.cache/indexes/tmux/panes/, meta.json for session/window/title/cwd; a pane's document is rewritten only when its text changed, and dropped when the pane goes away). Panes that host a live Claude session are skipped: their text is already in the conversation index, so nothing is indexed twice. At most the last 20000 lines of a pane are kept.

  • claude-history (prefix+C-c) and the usage panel: /fts word and /fts/tmux word add one row per matching pane (title = pane title, status tmux, the SESS/WIN/PANE columns filled); Enter goes to the pane (claude-history --focus-tmux %12: select its window and pane, focus the Hyprland window showing that session, else open a terminal attached to it).
  • alt-tab: the conversations table gains the same rows; its //tmux-session, //tmux-window, //tmux-title (and so //tmux) keys filter them. Any scope except live-only (/fts/live, which filters the window grid) shows the table.
  • focus-picker (prefix+w) lists panes, so /fts word / /fts/tmux word simply keeps the panes whose scrollback contains the word (!/fts word the others); other scope keys make it inert.
  • Composes with row filters: //tmux emacs /fts journ = panes whose tmux session/window/title contain "emacs" and whose scrollback contains "journ".
